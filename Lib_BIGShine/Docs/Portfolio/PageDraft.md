### ANATHEMA～忌まわしき影～

**ボスとの戦闘を題材に、ゲームとその制作を支える仕組みを実装する3Dアクション作品。**

## 2. 「制作詳細：MotionWarp」掲載本文

### 攻撃モーションの移動を、対象との位置関係に合わせて補正する

#### 対応する課題

攻撃モーションに含まれる移動をそのまま適用すると、対象との距離や方向によって、移動の終点が狙った位置と合わない場合があります。この位置関係を調整するため、RootMotionの移動量を補正するMotionWarpを実装しています。

#### 処理の流れ

1. AnimationControllerでRootMotionの移動差分を取り出し、ワールド空間の移動量を用意します。
2. アニメーションの正規化時間と移動差分をMotionWarpへ渡します。
3. 対象の位置とプリセットに基づき、指定区間の移動方向や移動量、向きを補正します。
4. 補正した移動差分をCharacterMovementへ渡します。CharacterMovementがない場合はTransformへ移動オフセットを渡します。

#### 実装上の工夫

**攻撃ごとに補正の性質を変える**

方向のみ、移動量のみ、方向と移動量、指定終点への補正を設定できます。開始・終了の正規化時間、補正の強さ、停止距離もプリセットで管理し、攻撃ごとの設定をGUIで編集してJSONへ保存できます。

**補正量に上限を設ける**

位置補正のフレーム単位・累積量、回転補正の速度・累積角度などを設定します。対象へ寄せる処理に制限を持たせることで、補正の強さを調整できる構造にしています。

**移動途中の対象への入り込みも判定する**

停止距離の判定では、移動後の位置だけでなく、水平面上の移動線分と停止円の最初の交点を求めます。終点が円の外側でも途中で円を横切るケースを扱い、許可する移動量を制限します。

**補正前後を比較できるようにする**

比較GUIで補正のON/OFFを切り替え、元の移動差分と補正後の移動差分を確認できます。設定を変更しながら補正の影響を調べるための仕組みです。

#### 掲載する映像・図の編集メモ

- 同じ攻撃・同じ開始位置・同じ対象位置で、MotionWarp OFFとONを並べて収録する。
- 正面から距離がずれた場合と、対象が斜めにいる場合の2例を用意する。
- 移動線分、対象の停止円、最初の交点を示す図を添える。
- 通常プリセットと敵からの明示対象要求には処理の違いがある。「すべてのモードで同じ上限を適用する」とは書かない。
- 説明するのは補正の仕組み。命中率や操作感の改善は、比較結果を確認してから追記する。

## 3. 「制作詳細：ボスAI」掲載本文

### 行動の履歴と現在の状況から、次の行動目的を選ぶ

#### 対応する課題

プレイヤーとの戦闘では、距離だけでなく、攻撃や防御の傾向を行動選択へ反映する必要があります。また、反応できる条件と頻度を調整するため、反応待ち時間や防御行動のコストを設定しています。

#### 判断と行動をつなぐ構造

人型ボスのAIでは、観測情報や履歴からIntentという行動目的を選択します。Intentには観察、攻め、防御、間合い調整、ガード対策、回避への対策などがあります。その目的による補正をBehaviorGraph側の行動選択へ渡し、条件を満たした候補の抽選に反映します。

処理の流れ：プレイヤーの観測 → 履歴・反応待ち時間の更新 → Intentの選択 → グラフの条件評価と重み補正 → Actionの実行

#### 実装上の工夫

**同じ行動の繰り返しを判断へ反映する**

同じ行動の反復回数に応じて反応待ち時間を補正し、ガードや回避の傾向も候補の重みへ反映します。ゲーム中の履歴をルールと重みへ反映する実装です。

**防御行動へ反応コストを設ける**

ガード、回避、ジャストガードには異なるコストを設定しています。反応用の予算は条件付きで回復し、残量は候補の可否にも使います。加えて、読み違いとして観察を選ぶ確率も設定できます。

**判断理由を画面で確認する**

GUIにはIntent、予算、反応までの待ち時間などを表示します。どの状況でどの目的を選んだかを確認しながら設定を調整できるようにしています。

#### 掲載する映像・図の編集メモ

- ガードを継続する場面、回避を繰り返す場面、間合いを離す場面で、Intentと重みの表示を収録する。
- 抽選を含むため、常に同じ反応になるとは説明しない。
- 人型ボス固有の判断処理と、共通のAIBehaviorGraphを図で分ける。ドラゴンにも同じ判断処理が入っているとは書かない。
- 機械学習、学習モデル、ニューラルネットワークという表現は使わない。今回確認した実装は履歴・条件・重みによる選択。
- 「理不尽さを解消した」「読み合いが面白くなった」といった体験面の結果はプレイ確認後に追加する。

## 4. 「制作詳細：演出エディター」掲載本文

### 本番の実行経路を使って、演出を編集・試写する

#### 対応する課題

カメラ、アニメーション、エフェクトなどの演出は、実行するタイミングや待機条件を合わせて確認する必要があります。そこで、既存のActionSequenceのデータをタイムライン上で編集し、実際のSceneで試写する機能を実装しています。

#### 実装上の工夫

**既存のActionSequenceとデータを共有する**

編集対象のSequenceをシリアライズして下書きに保持し、変更を元のComponentへ反映します。Actionの選択も既存の登録情報を使うため、演出の実行経路と編集用データの対応を保てます。

**試写前のSceneへ戻せるようにする**

試写開始時に元のSceneをメモリへ退避し、停止時は既存の復元経路を使います。試写中の状態を元の編集データへ混ぜないよう、試写中の適用や保存にも制限を設けています。

**巻き戻しは先頭から再評価する**

シークでは必要に応じてSceneを再構築し、固定1/60秒の更新を指定時刻まで再実行します。処理回数にはフレームごとの上限を設けています。任意の時刻の状態を直接復元する方式ではないため、遠い時刻への移動には再評価の時間が必要です。

**異なる時間基準を混同しない**

アニメーションに結び付いたActionは、絶対時刻へ推測変換せず、Animation-boundとして表示します。Sequenceの時計、アニメーションの再生位置、エフェクトの経過時間も確認できます。

#### 掲載する映像・図の編集メモ

- Actionの時刻変更 → 試写 → シーク → 停止・復元の順に操作を収録する。
- 既存のDocs/K2Presentation/editor-01.jpgは戦闘画面であり、このエディターの証拠画像として使わない。該当画面を特定するか、本人が改めて撮影する。
- 試写時間の短縮率は未計測。作業効率が何倍になったといった数値は掲載しない。
- 「任意時刻へ瞬時にジャンプ」「すべての演出を一本のタイムラインへ展開」とは書かない。
