ライブラリー基板設計 説明メモ

目的
このメモは、各機能の土台になっている GameObject、Component、Manager、Serialize、Resource、Editor、ActionRegistry、Blackboard などを説明するための入口。
個別機能ではなく、「なぜ機能を追加しやすい構成になっているか」を説明するために使う。

この基盤を一言で説明するなら
GameObject に Component を追加し、Component を Serialize / Editor / Manager / ActionRegistry と連携させることで、機能を追加しやすくした自作ゲームライブラリの土台。

説明の中心
- GameObject が Component を持つ
- ComponentBase が Start、Update、Gui、Serialize、Deserialize の共通入口になる
- ComponentRegistry で JSON から Component を復元できる
- RegisterAllComponents で使用する Component を登録する
- GameObjectManager が Object と各種 Manager を管理する
- ResourceManager / ModelResourceManager / TextureResourceManager が Asset の読み込みを担当する
- EditorWindowManager が Editor Window を管理する
- ActionRegistry が Sequencer や Component 間の呼び出しに使われる
- BlackboardComponent が状態や値の共有に使われる

全体フロー
1. Scene や JSON から GameObject を作る
2. ComponentRegistry を使って Component を生成する
3. Deserialize で保存データを復元する
4. Start で初期化する
5. Update で毎フレーム処理する
6. Gui で Editor から調整する
7. Serialize で JSON に保存する

1. GameObject / Component 設計
2. ComponentBase の共通関数
3. ComponentRegistry と RegisterAllComponents
4. Serialize / Deserialize の考え方
5. Manager の役割分担
6. Resource 管理
7. EditorWindow 管理
8. ActionRegistry
9. BlackboardComponent
10. 良い点と改善点

良い点
- Component 単位で機能を追加しやすい
- Editor と Runtime の入口が共通化されている
- JSON 保存により、シーンや Asset をデータとして管理できる
- ActionRegistry と Blackboard により、機能間の連携を作りやすい
- Manager を分けることで、Object、Resource、Effect、Attack などの責務を分離できる

改善点
- Component が増えるほど RegisterAllComponents の管理が重要になる
- Serialize の互換性を保つため、古い JSON への fallback を意識する必要がある
- Component 間依存が増える場合は、依存方向をメモに残すと保守しやすい


============================================================
1. ライブラリー基盤の全体概要
============================================================

このプロジェクトの基盤は、GameObject に Component を追加して機能を組み立てる Component 指向の構成。

GameObject は Transform や複数 Component を持ち、Component は Start、Update、Gui、Serialize、Deserialize を通して Runtime、Editor、保存処理へ参加する。
ComponentRegistry により、JSON に書かれた Component 名から実際の Component を生成できる。

ActionRegistry と BlackboardComponent は、Animation、AI、Combat、Particle などの機能をつなぐための共通の仕組み。
ResourceManager 系は Model、Texture などの Asset 読み込みを担当し、EditorWindowManager は Editor Window を管理する。

一言で説明するなら、
「GameObject / Component / Manager / Serialize / Editor を共通化し、各機能を追加しやすくした自作ゲームライブラリの土台」
と言える。


============================================================
2. この基盤を作った理由
============================================================

解決したかった問題
- 機能を追加するたびに GameObject クラスを直接改造すると拡張しづらい
- Scene 保存や読み込みを機能ごとに個別実装すると重複する
- Editor で Component ごとの設定を触れるようにしたい
- Animation、Combat、AI、Particle などを疎結合に連携させたい
- Model や Texture の読み込みを毎回個別に書きたくない

この設計で改善したこと
- ComponentBase に共通の入口を持たせた
- ComponentRegistry で JSON から Component を復元できるようにした
- Serialize / Deserialize により、Scene や Asset を保存できるようにした
- ActionRegistry により、文字列 Action で Component 間呼び出しを行えるようにした
- BlackboardComponent により、状態やパラメータを共有できるようにした
- Manager を分け、Object、Resource、Effect、Attack などの責務を整理した


============================================================
3. GameObject / Component
============================================================

GameObject
- 主な責務:
  Scene 上の1つの Object を表す。
  Transform と複数の Component を持つ。
- 説明のポイント:
  プレイヤー、敵、エフェクト、カメラ、ライトなどを同じ GameObject の仕組みで扱える。

ComponentBase
- 主な責務:
  各 Component の共通インターフェース。
- 主な関数:
  GetName
  Start
  Update
  Gui
  Serialize
  Deserialize
- 説明のポイント:
  Runtime 処理、Editor 表示、JSON 保存の入口を Component ごとに持たせている。

Component の例
- AnimationControllerComponent
- ParticleComponent
- MeshVFXComponent
- AIControllerComponent
- PlayerControllerComponent
- HealthComponent
- HitBox
- CameraComponent
- LightComponent

処理フロー
1. GameObject が作られる
2. 必要な Component を AddComponent する
3. Start で初期化する
4. 毎フレーム Update する
5. Editor 表示時に Gui を呼ぶ
6. 保存時に Serialize する
7. 読み込み時に Deserialize する


============================================================
4. ComponentRegistry / Serialize
============================================================

ComponentRegistry
- 主な責務:
  Component 名と生成関数を対応付ける。
- 説明のポイント:
  JSON に保存された Component 名から、実際の Component インスタンスを復元するための仕組み。

RegisterAllComponents
- 主な責務:
  使用する Component をまとめて登録する。
- 説明のポイント:
  新しい Component を追加したら、ここに登録しないと JSON から復元できない。

Serialize の考え方
- Component ごとに自分の保存データを JSON に書く
- GameObject は Component のリストを保存する
- Scene 読み込み時に ComponentRegistry を使って復元する
- 古い JSON にキーがない場合はデフォルト値で読む

良い点
- Component 単位で保存処理を分けられる
- 新しい機能を追加しても、既存 Scene への影響を小さくできる
- Editor で調整した値をそのまま保存しやすい

注意点
- Component 名を変えると古い JSON が読めなくなる可能性がある
- 登録漏れがあると Deserialize できない
- ポインタや GPU Resource は JSON に保存せず、パスや設定値だけ保存する


============================================================
5. Manager の役割
============================================================

GameObjectManager
- Scene 内の GameObject を管理する
- Object の生成、検索、削除の入口
- AttackSystem や EffectManager などの System へアクセスする入口にもなる

ResourceManager
- 共通 Resource 管理の土台
- Asset の読み込みやキャッシュの考え方をまとめる

ModelResourceManager
- ModelResource の読み込み、キャッシュを担当する
- glTF や独自形式の読み込み結果を共有する

TextureResourceManager
- Texture の読み込み、SRV 管理を担当する
- 同じ Texture を何度も読み込まないようにする

EffectManager
- Particle / MeshVFX の Asset Cache と一時生成を管理する
- HitEffect や AttackEffect から呼ばれる

AttackSystem
- 攻撃インスタンスやヒット履歴を管理する
- Combat の多段ヒット制御や重複ヒット防止に関わる

EditorWindowManager
- Editor Window の生成、表示、管理を担当する
- Animation、Particle、AI、PostEffect などの Window を扱う


============================================================
6. ActionRegistry
============================================================

目的
ActionRegistry は、文字列名で処理を登録し、別のシステムから呼び出せるようにする仕組み。

使われる場面
- Animation Sequencer から Particle を Trigger する
- Animation Sequencer から HitBox を有効化する
- AIBehaviorGraph から AI Action を呼ぶ
- Component が自分の操作を Action として公開する

設計上の利点
- 呼び出し側が具体的な Component 型を知らなくてもよい
- Editor で Action 名を選べる
- Animation や AI のデータから Runtime 処理を呼びやすい

注意点
- Action 名が文字列なので、名前変更時に参照切れが起きる
- 同名 Action の衝突に注意する
- 登録解除のタイミングを整理する必要がある


============================================================
7. BlackboardComponent
============================================================

目的
BlackboardComponent は、複数の処理で共有する値をカテゴリごとに管理する仕組み。

使われる場面
- Animation の遷移条件
- Animation Event から Combat への値渡し
- AI の判断条件
- GameMode や Director の共有状態

値の例
- float
- int
- bool
- string
- Vector2
- Vector3

設計上の利点
- 状態やパラメータを Component 間で共有しやすい
- Editor から値を確認、変更しやすい
- AI や Animation の条件判定をデータ駆動に近づけられる

注意点
- 文字列キーの管理が重要
- どの Component が書く値か、どの Component が読む値かを整理する必要がある
- 型違いで読まないように注意が必要


============================================================
8. Editor との関係
============================================================

Component の Gui
- 各 Component が自分の設定 UI を持てる
- Scene 上の Object を選んだ時に Component ごとの設定を編集できる

EditorWindow
- Animation Editor
- Particle Editor
- AIBehavior Editor
- PlayerState Editor
- PostEffect Window
- GameMode Window

設計上の考え方
- Component に近い設定は Component::Gui に置く
- 複雑な編集や専用画面が必要な場合は EditorWindow に分ける
- 編集した値は Serialize で JSON に保存する

説明例
「Runtime 用の Component と Editor 用の Window を分けつつ、Component 自体も Gui を持てるようにしています。
簡単な設定は Inspector 的に Component::Gui で触り、複雑なグラフやシーケンサーは専用 Window で編集します。」


============================================================
9. データフロー
============================================================

Scene 読み込み
1. Scene JSON を読む
2. GameObject を生成する
3. Component 名を見て ComponentRegistry から生成する
4. Component::Deserialize で値を復元する
5. Resource Path があれば Manager から読み込む
6. Start で Runtime Resource を作る

Editor 編集
1. Editor で Component の値を変更する
2. 必要に応じて Runtime Resource を Rebuild する
3. Save で Serialize する
4. JSON に保存される

Runtime
1. GameObjectManager が GameObject を管理する
2. 各 Component の Update が呼ばれる
3. Manager / System が横断的な処理を行う
4. RenderSystem が描画する
